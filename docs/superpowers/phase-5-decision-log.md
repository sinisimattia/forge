# Phase 5 — Decision Log

The rulings made while building Forge's Phase 5 — multi-factor authentication —
preserved from the execution ledger so they survive it.

Its companions are `phase-1-decision-log.md` through `phase-4-decision-log.md`.

**This phase's signature defect is not a new one, and that is the finding.** Phase 3 already
named it — *prose that asserts something the code does not do* — and wrote the rule against it.
Phase 5 produced it more than fifteen times anyway, in a phase whose every brief carried that
rule in bold. Three separate fix waves were dispatched at it; the final re-review still found
two more. So the useful output is not the rule, which existed, but the diagnosis of why having
the rule did not help:

> **Almost every instance was TRUE when written.** The ones that rotted share a form: they
> **enumerate**. "Both callers hold the lock." "Eight call sites." "`mapMfaMethodRecord` is the
> one place that reads them." "the only test that fails if these two lines go." A count is a
> claim about the whole codebase, made in a comment that only sees one file, and it goes false
> the next time anyone adds a caller — silently, in a file no diff touches.

The remedy that finally worked was not more care. It was a change of form: **state the
invariant, not the enumeration.** "Both callers hold the lock" became "every caller holds a
write lock, and nothing here enforces that" — which survives a fourth caller, and additionally
says the true and useful thing, that the property is unguarded. Every enumeration in the phase
was replaced this way rather than recounted, because a corrected count merely resets the clock.

Two corollaries, both paid for:

1. **A correction inherits the framing of what it corrects.** One sentence in
   [ADR-0012](../../template/docs/adrs/0012-a-second-factor-is-a-property-of-the-account.md)
   was written false three times running, by three different authors, each of whom read the
   code first. Every attempt enumerated who mints a `LOGIN` challenge; the enumeration is three
   deep across three files, and each author checked, found two, and stopped at the file they
   were in. The fourth attempt deleted the clause instead — the ADR's argument never needed it.
2. **The instruction can be the defect.** `phase-roadmap.md`'s "`AuditAction` at 33 members"
   was reported as stale by the whole-branch review, carried as stale in the ledger, and
   written into a fix brief as a fix-now item. It is correct: it sits under *"What Phase 5
   inherits, already built"* and describes Phase 4's end state. The implementer read the
   section heading, concluded that everyone above it was wrong, and refused. Nothing else in
   the process would have caught it, because every other check asks whether work matches its
   instructions.

## 1. The flaking 401s (Task 1) — investigated, not reproduced, not fixed

**What this is.** Three backend specs — `src/__tests__/discriminating/d9-tenant-isolation.spec.ts`,
`src/auth/__tests__/change-password.spec.ts`, `src/organizations/__tests__/members.controller.spec.ts`
— have been reported flaking as spurious 401s across two prior phases. Phase 3's log records
a load-sensitive flake with the same shape in two of these files (`invitations.controller.spec.ts`
and `members.controller.spec.ts`), neither reproduced on retry, capped at 2 runs. Phase 4's log
names all three together for the first time and states the hypothesis that matters: the common
symptom — spurious 401s under a parallel jest runner — "points at shared session or identity
state across workers", investigated as one item, under a bounded budget, rather than chased.

This task is that investigation. It carries no MFA code, by design: Phase 5 is about whether
sessions get issued, so the suite that will judge every later task in this phase has to mean
something first, before any of that code is written.

The brief's cap was **20 suite runs or 30 minutes of wall clock, whichever came first**

Controller's ruling, recorded here rather than re-argued: **the overrun was the right call and

which is exactly the "shared session or identity state across workers" shape Phase 4's log
named — so they bought information a stop at 20 would have foreclosed. The
CPU-oversubscription run is the only attempt in this investigation to test the
load-sensitivity framing both Phase 3's and Phase 4's logs use for this flake. Both were worth
the overrun; neither was recorded as a deviation at the time, and this paragraph is that
correction, added on review rather than at the time it happened.

**Wall-clock timing:** only partially recoverable, from the shell `date` calls that happened
to bracket each batch. The jest invocations themselves — all 31, summed — ran between 17:23:34
and 17:27:57 local time, about **4 minutes 23 seconds** of combined shell-loop-plus-test-execution
time. That is the only span that was actually timestamped. The work before it (reading the
brief and the three specs, reading `tenancy-world.ts` and `discriminating/world.ts`, two failed
`npm install` attempts against the un-substituted template, generating a scratch project with

this log, running `sanitize`, committing) were not timestamped and cannot be reconstructed
precisely now. **This is a gap in method, not a claim that the 30-minute leg governed instead
of the 20-run one** — the 4m23s recorded for test execution is comfortably under 30 minutes on
its own, but it is a measurement of test execution alone, not of total task wall-clock, and
this log should not be read as certifying the latter one way or the other.

### Hypotheses, and their status

1. **`JWT_SECRET` (or any signing key) generated per worker process, so a token minted in one
   worker is invalid in another — the leading hypothesis named in the brief, and the cheapest
   to check.** **ELIMINATED**, by direct inspection rather than by failure to reproduce — but
   the elimination was first written up against the wrong file, and this paragraph corrects
   that rather than papering over it.

   `src/common/testing/tenancy-world.ts` (`makeTenancyWorld`) is **not** in the dependency path
   of any of the three specs under investigation. Read directly, it defines no `SIGNING_KEY` or
   `JWT_SECRET` at all and mints no token — it constructs `OrganizationsService`,
   `AuthorizationService`, `PrincipalService` and `AuditService` over a `FakeDataSource`, and
   nothing else. Its only importer, checked directly
   (`grep -rln 'tenancy-world' src` → one hit, `src/common/testing/index.ts`, the barrel), is
   that barrel, and all three specs under investigation import only `FakeDataSource` from it
   (`import { FakeDataSource } from '../../common/testing'` — `change-password.spec.ts:31`,
   `members.controller.spec.ts:18`, `discriminating/world.ts:26`), never `makeTenancyWorld`.
   `tenancy-world.ts` is out of scope for this elimination because nothing under investigation
   calls into it and it carries no signing-key mechanism to eliminate in the first place. (It
   is, separately, the world behind `organizations.conformance.spec.ts`,
   `organizations.security.conformance.spec.ts` and `authorization.conformance.spec.ts` — none
   of which are among the three specs this task investigates.)

   The file that actually carries `d9-tenant-isolation.spec.ts`'s signing key is
   `src/__tests__/discriminating/world.ts` — the local `./world` the spec imports from, a
   separate file from `tenancy-world.ts` despite the similar name. It defines
   `const SIGNING_KEY = 'discriminating-spec-signing-key'` at line 92. Alongside it,
   `change-password.spec.ts:87` defines `'change-password-spec-signing-key'` and
   `members.controller.spec.ts:64` defines `'members-controller-spec-signing-key'` — each a
   fixed string literal, declared once at module scope in the spec file itself (or, for d9, in
   the `world.ts` it imports), and handed to both the
   `ConfigModule.forRoot({ load: [() => ({ JWT_SECRET: SIGNING_KEY })] })` that configures the
   guard's `JwtStrategy` and the `JwtModule.register({ secret: SIGNING_KEY, ... })` or
   `new JwtService({ secret: SIGNING_KEY, ... })` that mints the token the spec sends. Neither
   value is derived from `Math.random()`, `crypto.randomBytes()`, `process.pid`,
   `JEST_WORKER_ID`, or any other per-process or per-run input — grepped for directly
   (`grep -rn '^const SIGNING_KEY' src`), found nowhere in any of these three files, in
   `discriminating/world.ts`, or anywhere else in the backend. A token minted in one worker
   cannot be invalid in another because both sides of the comparison, in every worker, use the
   same hard-coded string. This mechanism cannot be the cause.

2. **Shared mutable state across jest workers or across the three spec files** (a module-level
   binding, or a fixed email/subject id reused so two workers register the same account).
   **ELIMINATED for these three files specifically.** Each constructs a brand-new
   `FakeDataSource` (an in-memory store, not a real database) inside `beforeEach`, so no state
   persists even across two tests in the *same* file, let alone across files. Jest gives every
   test *file* its own module registry regardless of `--maxWorkers` or `--runInBand` — that is
   true even in a single-worker serial run — so a module-level `const` or `let` in one of these
   files is not observable from another file under any parallelism setting. None of the three
   files opens a real network port (`grep` for `.listen(`, `createServer` found nothing), so
   there is no shared-port mechanism either. This does not rule out the same phenomenon for
   some *other* pair of files not in scope here, only for these three.

3. **A race between concurrent requests inside a single spec** (e.g. `Promise.all` of
   overlapping requests against shared session state). **ELIMINATED for these three files.**
   None of the three issues concurrent requests; every request in every test is a sequential
   `await`. (`Promise.all`/`Promise.allSettled` do appear elsewhere in the backend suite — e.g.
   `auth.service.spec.ts`, `refresh-rotation.spec.ts` — but not in the three files under
   investigation.)

4. **Load-sensitivity** (fails under CPU contention or a constrained CI runner, passes on an
   idle fast machine) — the framing both Phase 3's and Phase 4's logs use, and the one this
   investigation could not itself rule in or out. **NOT CONFIRMED, NOT ELIMINATED.** One run
   was made under artificial CPU oversubscription (16 jest workers on 8 cores, plus six
   busy-loop background processes) specifically to test this, and it still passed clean. That
   is weak evidence against it, not strong evidence against it — GitHub Actions' shared runners
   (2 vCPU) are a different machine, a different OS (Linux vs. this investigation's macOS), and
   a different scheduler than anything reproduced here, and a `yes` loop does not reproduce
   whatever specific resource CI is short on (which could be scheduler latency, disk I/O, or
   memory pressure rather than raw CPU).

### What was changed

**Nothing.** No fix was applied, because no defect was found to fix. Speculatively changing
test code to address a bug that could not be reproduced or located would trade a known-flaky
suite for a suite that is unverifiably different — a worse position, not a better one. Per the
brief's own Step 4, the eliminated hypotheses are recorded here instead.

### The measured failure rate after

Unchanged: 0 failures observed, out of 31 jest invocations, because no change was made.

### Is a green backend suite now evidence for a security property?

**Not fully, and this task does not change that.** `d9-tenant-isolation.spec.ts` is a
discriminating security test — the property phase 4's log put in one sentence:
*"a green suite is not evidence"* is, unaltered, still this project's position after this
task. What this investigation adds is narrower and still useful: **the specific mechanism most
likely to make a green run mean nothing — a signing key that differs between the token a spec
mints and the guard that checks it — is not present.** Every signing key involved in these
three files is a fixed literal, identical on both sides of every comparison, in every worker,
every time. That particular way for a 401 to be spurious cannot happen here.

What remains true, unchanged from Phase 3 and Phase 4: **the flake itself has not been
reproduced, at this commit, on this machine, in 31 runs across five configurations including
one built to induce load-sensitivity.** A reviewer reading a green run of these three specs in
this environment has 31 consistent data points behind that green, and a specific leading
hypothesis ruled out by code, not merely by absence of failure — which is more than either
prior phase had. A reviewer reading a green run of these three specs **in CI** has exactly what
Phase 3 and Phase 4 had: a suite that has been observed to fail intermittently, for a reason
still not identified, under conditions (CI's specific runner, its specific parallelism, its
specific load) that were not reproduced here. Treat a red run of any of these three specs in CI
as informative regardless of this record; treat a green run in CI the way Phase 4 already
recorded — as not, on its own, proof that the property it names holds, until the mechanism is
found or the flake stops being observed over a long enough run of CI history to call it gone.

Task 1's contribution is: one plausible mechanism ruled out by inspection, five more
reproduction attempts on record (31 runs total, up from Phase 3's 2 and Phase 4's unspecified
count) that all came back clean, and this statement carried forward explicitly rather than
left to be rediscovered by whoever reviews Phase 5's later tasks.

## 3. The design rulings, and what each costs if wrong

**A second factor belongs to the account, not to the road in.** Recorded as
[ADR-0012](../../template/docs/adrs/0012-a-second-factor-is-a-property-of-the-account.md). The
tempting design attaches the factor to the password form, because that is the path in front of
the developer. It is wrong in a way that looks finished: the federated callback is a second door
into the same account, and if it does not ask, the account is exactly as strong as the weaker of
its two doors while its owner believes otherwise.

**A single-use `mfa_challenges` row, not a stateless JWT.** A stateless challenge cannot be
revoked and cannot be spent exactly once without server state anyway; having accepted the state,
the row is simpler and the single-use property becomes one conditional `UPDATE`. *Cost if wrong:*
a table and a cleanup concern that a JWT would not have needed.

**WebAuthn shipped alongside TOTP, not after it.** *Cost if wrong:* a materially larger phase.
Paid, and it surfaced the challenge-lifecycle questions TOTP alone would have hidden.

**`type` and `purpose` are plain `text` with no CHECK constraint.** The values are pinned in
TypeScript and by a hand-written map; a CHECK would make adding a member a migration.

**No foreign key on `audit_entries`, in either direction — ever.** A referential action runs with
the table owner's privileges, which voids the append-only property discriminating test D13 exists
to guard. This is a standing constraint, not a Phase 5 decision, and is restated here because the
phase added a member to `AuditAction` and the temptation recurs.

**The purpose allowlist is kept separate from the `!== expected` comparison.** They answer
different questions: the allowlist refuses what the file does not model, the comparison refuses
what this caller did not ask for. Collapsing them passes every test today and stops refusing an
unmodelled purpose the day a third member joins the enum. This was nearly deleted twice during
the phase — both times because every existing test passed a *modelled* `expected`, so the
allowlist could be removed and the suite stayed green. The test that reds is one of a specific
shape, and it now exists.

## 4. `SecondFactorSettled` — a guarantee the compiler holds

The property "no session opens without evidence the second factor was settled" was enforced by
review and by tests, which is to say by vigilance. Task 20 moved it into the type system:
`SessionService.begin` and `beginIn` require a `SecondFactorSettled`, which has a private member
and a private constructor and can only be obtained from a factory corresponding to a real
settlement.

What makes this more than a type is the **fault injection, made permanent**. A sixth caller,
written the way someone would actually write it:

```ts
impersonate(target, client) { return this.sessions.begin(target, client); }
```

fails with `TS2554: Expected 3 arguments, but got 2`. Three further injections confirm the
evidence cannot be manufactured: `TS2345` (the private member), `TS2673` (the private
constructor), and `TS2339` — the compiler refusing evidence to a caller that never narrowed to
the challenge branch. All five resulting directives live in the suite as `@ts-expect-error`,
**and a `@ts-expect-error` whose line starts compiling is itself an error**, so each one fails
the build on exactly the change that would reopen the hole. The injection stopped being a
demonstration and became a standing guard.

Two things stated honestly rather than glossed:

- `{} as SecondFactorSettled` still compiles. A *shaped* cast does not (`TS2352`). The guarantee
  is "not by accident", not "not by a determined caller", and it is documented that way on the
  class. No call site in the codebase contains such a cast.
- The guard is live in **one** tier, not two: `npm run typecheck` and CI's
  `nx affected -t typecheck`. It is not live under jest, because `tsconfig.base.json` sets
  `isolatedModules: true` and ts-jest therefore transpiles without checking. The comment
  originally claimed two tiers; that claim was wrong and is corrected. The overstatement was the
  dangerous direction — a reader who believes it can delete the typecheck step thinking jest
  still covers the guards, taking the count to zero.

## 5. What the reviews caught that no task review could have

Three findings needed a view of the whole branch, and none of them is a defect within any single
task's diff:

1. **`WebAuthnCeremonies.loginOptions` spent a `LOGIN` challenge and wrote no audit entry**, on
   either refusal or success. Every other second-factor path records its refusals; probing this
   one left no trace. Each task's audit behaviour was correct inside its own diff; the gap
   existed only in the comparison between them.
2. **`loginOptions` did not re-check `canAuthenticate()`**, while its sibling `spendChallenge`
   did — and that sibling's comment ended *"Same predicate, so the two answers cannot drift
   apart."* A third spender had appeared and the sentence had quietly become false. So the same
   line was simultaneously a behavioural gap and an instance of §0's defect.
3. **Stale pointers in files the diff marks unchanged.** When a symbol moves, every comment
   describing its old home rots in a file no reviewer of that change will open. A diff-scoped
   review structurally cannot find these; only a whole-tree grep for the moved symbol can.

**The falsification standard, applied late and worth applying early.** The final waves did not
assert that their new tests worked — they removed the code, confirmed that *exactly* the intended
tests failed and no others, and restored. That is the difference between a test that passes and a
test that discriminates, and it caught nothing only because it was done; earlier in the phase, two
assertions that had never been watched go red turned out not to discriminate at all.

## 8. What Phase 6 inherits

Carried deliberately, each with the reason it was not done here:

| Item | Why deferred |
|---|---|
| **No throttling anywhere** — not on code submission, not on challenge minting | the largest gap in this phase. A 6-digit TOTP code with unlimited attempts is a 6-digit code. It is a cross-cutting concern that wants one mechanism, not five call sites |
| **Unbounded method enrollment** | no limit on how many factors an account may enrol |
| **base64url recovery codes** | a poor alphabet for something a person transcribes by hand from paper |
| **`ix_mfa_challenges_expires_at` missing** | cleanup scans without it |
| **Nobody is told how many recovery codes remain** | no count in `GET /mfa/methods`, no endpoint, nothing in the security screen. A person cannot know they are on their last one |
| **`loginOptions` rolls the challenge TTL indefinitely** | each ceremony mints a fresh challenge; the fix is a `mint` signature change |
| **Duplicate-credential check outside the transaction** | a concurrent double-enroll of one key answers 500 instead of 409. Correctness holds — the unique index still refuses it. Deferred because the fix moves a transaction boundary and no review wave remained to catch a regression |
| **The flaky-401 trio, still unreproduced** | §1. Three phases of investigation, capped each time |
| **Dev Storybook crashes while the build passes** | the build is gated; the dev server is not |
| **The real-Postgres confirm walk** | covered by the fake, not by the container tier |
| **`decideMfaRemoval`'s no-reauth shape** | removing a factor asks for no second proof |
