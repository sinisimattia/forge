# Internationalization (i18n)

This document states the **philosophy** only. The framework mechanics — `nestjs-i18n`
in the backend versus `@nuxtjs/i18n` in the webapp, the translation-file layout, key
typing, and where translation happens — live in each package's `STANDARDS.md`.

## Principles

- **Never hard-code user-facing text — ever.** Every user-facing string must go through
  an i18n layer. This includes template text, labels, placeholders, titles, `aria-label`
  attributes, headings, button text, status labels, empty states, and validation, error,
  and toast messages — and, on the backend, every exception message, validation message,
  and response `message`.
- **English is the official, default, and only locale.** There is no other locale today.
  Do not add one or reference one. Adding a locale later is a matter of dropping in a new
  translation folder — no code changes.
- **Add the translation key first.** When introducing any new user-facing string, throw,
  response message, or field, add the key to the relevant translation file *before*
  referencing it.

> Protocol identifiers are not user-facing text and are not localized (for example, the
> canonical HTTP reason phrase in an error's `error` field).
